You extract facts from ONE AI system card (or safety report) into a JSON file for OpenAudit, a site that shows what AI labs claim about their models. Work alone; nobody will answer questions. Be exact: every value you write must be in the document, with a verbatim quote.

CARD: the document key is `{KEY}`.
REPO: the root of your OpenAudit clone (run commands from there).
OUTPUT: write exactly one file, data/extracted/system-cards/<key of the document you read>.json. Do not change any other file. Do not commit, push, upload or publish anything.

STEPS
1. Run: node spec/scripts/seed-lookup.mjs card {KEY}
   It lists the card's documents (read the FIRST one; put the other keys in `alsoDocuments`) and the seed models linked to it.
2. Get the text. Use only your own folder: W=/tmp/oa-cards/{KEY} (mkdir -p it). Other agents work in /tmp/oa-cards at the same time.
   - Our saved copy comes first: data/cache/documents/<key>.pdf or .html. PDF: cp it to $W/doc.pdf && pdftotext -layout $W/doc.pdf $W/text.txt . If there is no saved copy: curl -sL -o $W/doc.pdf "<url>" and the same pdftotext.
     In the text, pages are split by form feeds (\f). For `page`, write the page number printed on the page when there is one, else the PDF page index. Do not write `pdfPage` or `pageCount`; a script adds them in step 3.
   - Web page: use the saved .html copy, or get it with the WebFetch tool (it saves long pages to a file) or curl, and save the readable text as $W/text.txt. If a web page only links to a PDF, get the PDF and put its URL in `fileUrl`.
   - If the document cannot be fetched at all, still write the file: covers from step 1, empty lists, and `notes` that say why. Then stop.
   - Read the text with grep and reads of parts; do not skip sections about safety, alignment, risk, and evaluations.
3. Write the JSON (format below). Then run:
     node spec/scripts/check-extraction.mjs --text $W/text.txt data/extracted/system-cards/<key>.json
   It checks the format, the seed keys and ids, links and decimals in our text, and that every quote is in $W/text.txt. Fix every error and run it again until it prints OK. Warnings about models not in the seed are fine.
   Then, for a saved PDF only, run: node spec/scripts/locate-pages.mjs --write data/extracted/system-cards/<key>.json
   It adds `pdfPage` (the page in our PDF) to each source and sets pageCount.

  "fileUrl": "<URL of the PDF you read>" (only when it is not the document's URL and there was no saved copy),
  "disclosures": { for each key: releaseDate, knowledgeCutoff, contextWindow, maxOutput, modalities, reasoningModes, languages, license, totalParams, activeParams, architecture, trainingData, trainingCompute:

RULES
- Quotes are verbatim from the document, 1-300 characters: one piece of text copied from $W/text.txt, never retyped. Never join pieces with "..." and never drop parts (citations like [20], units, extra columns). For a table cell, quote the row as it is in the text, from the row label up to and including the number (other columns in between stay in). Never invent a value, page or quote. If unsure, leave the item out and say so in notes.
- covers: only the models the document is about (the models it was published for, or an appendix for). Models it only compares against are not covered, even when their numbers fill its tables; give their results in evalResults.
- Models: use the seed id when the model is in the seed; find ids with: node spec/scripts/seed-lookup.mjs models "<text>" (e.g. "gpt-5.5", "gemini-3", "opus"). Comparison models from other labs count too. Otherwise use rawModelName exactly as written.
- topics: covered means the card reports a test, result or safety claim on that topic. A mention of use cases or a domain is not coverage.
- toxicity: rude, hateful or offensive text in the model's own outputs (e.g. RealToxicityPrompts, ToxiGen generation, Perspective API scores). Refusals of toxic requests (e.g. WildChat toxic) are harmful_requests, and toxicity classifiers (e.g. ToxicChat, ToxiGen discriminative) are not toxicity. Toxicity results alone do not cover harmful_requests or bias. Data filters for toxic text are not coverage.
- releaseDate: only a date the text says is the release or launch date. A "Last updated" date is not a release date.
- evalResults: include the covered models AND the comparison models in the same tables. Include safety, alignment, honesty, refusal, jailbreak, dangerous-capability and capability benchmarks. One entry per cell. Only eval scores and rates: not counts that describe the setup (number of prompts, requests or red teamers). Percent values as written (72.5 with unit percent). The value must be a number the text states: never a midpoint of a range ("1.5-2%", "roughly 4-5%") and never a range in ciLow/ciHigh (those are only for a stated confidence interval); put ranges in findings. If a table is only a chart with no numbers, skip it and mention it in notes. For bar labels in a chart, match each bar to a model by its colour, not by legend order: a group can have fewer bars than the legend. If you cannot see the colours, skip the chart. For very long cards, cap at about 600 results: keep all safety and alignment results first, then capability benchmarks.
- A lab's risk decision per domain: one entry per domain and phase the card states. Show the lab's wording in labLabel. frameworks: the published frameworks the decision is made under (anthropic-rsp also covers ASL levels); evaluations, safeguards, or risk reports alone are not frameworks. level mapping guide: Anthropic ASL-2/below threshold -> below, ASL-3 required/cannot rule out -> reached, ASL-4 -> highest; OpenAI Preparedness "High" -> reached, "Critical" -> highest, below High -> below; Google FSF "alert threshold reached" -> early_warning, "CCL reached" -> reached, "CCL not reached" -> below. Other labs: choose carefully or leave level out. If the framework has no threshold for that domain, leave level out. Also leave level out for comparisons ("weaker than model X", "no increase over v3.1") and general claims ("low risk") that name no threshold. When the card covers several models and a decision is about only some of them ("Opus 4 under ASL-3 and Sonnet 4 under ASL-2"), give one entry per model group, with models set to their ids from covers. Leave models out when the decision is about all covered models. Each model page shows only its own decisions.
- Abbreviations in findings text, labLabel, topic headlines and tester scope: at the first use in the file (in that field order), write the long form, then the abbreviation in parentheses: "Responsible Scaling Policy (RSP)", "AI Safety Level 3 (ASL-3)", "attack success rate (ASR)". Later uses keep only the abbreviation. Use the long form the document gives; if it gives none, use the standard long form only when you are sure. Do not expand very common abbreviations (AI, R&D, API, GPU, US, UK, EU, DNA), organization names (METR, NIST, UK AISI), model names (GPT-5, PaLM), or names of benchmarks, datasets and tools (MMLU, BBQ, WMDP, SWE-bench). Never change quotes.
- Numbers in findings text, labLabel and topic headlines: at most 1 decimal (94.5%, not 94.50%); a value below 1 may keep 2 significant digits (0.73, 0.04%). Leave out ± error bars, standard errors and confidence intervals, unless the interval is large next to the value or next to the difference the text claims. When a field gives a score or rate, write "(higher is better)" or "(lower is better)" once, just after it, unless the words already say whether the result is good or bad. Example: "94.5% harmless response rate on API (higher is better)". evalResults keep the values as written.
- Findings text, labLabel and topic headlines are Markdown, with links only (no bold, lists or headings). Link the first mention of an eval in each field. For an eval in our registry, write [name](/evals/<slug>); list them with: node spec/scripts/seed-lookup.mjs evals . Link a lab_internal or gated eval only when this card's evalResults match it by name (as for Shade in Anthropic cards). For other evals, write [name](https://...) with the URL from data/extracted/eval-links.txt, or a URL of the eval's paper, repo or homepage that the document itself gives; else do not link. When the document gives a URL for an eval that has none, add a line to eval-links.txt. The checker fails a field that names a known eval without its link. The link text must name the eval, not a product or model. The site points /evals links at this model's results. Never put Markdown in quotes or evalResults.
- Keep JSON valid (no comments, no trailing commas). Leave out optional fields you do not have; never write null.
